## 1. What "100k decisions" means for each recipe, and why it is not one directory name

The batch (`PHASE_PLAN` amendment (aa) + revisions, `paper/LADDER_N_PILOT_LOG_2026-09-11.md`) runs
three recipes at different total budgets, with checkpoints archived at fixed **fractions of each
run's own budget** (`baselines/rl/train_rlpd.py` `ArchiveCheckpointCallback`, directory name
`ckpt_<pct>` where `pct = round(100 * step / total_budget)`):

| recipe | budget | checkpoint fractions | directory holding `ckpt_step=100000` |
|---|---:|---|---|
| `nested_ramp` | 250k decisions | 16 % / 40 % / 100 % | **`ckpt_040`** (100 000 / 250 000 = 40 %) |
| `nested_sparse` | 250k decisions | 16 % / 40 % / 100 % | **`ckpt_040`** (same arithmetic) |
| `staged` (tip-guard control) | 100k decisions | 40 % / 100 % | **`ckpt_100`** (100 000 / 100 000 = 100 %, i.e. the FINAL checkpoint) |

So "the 100k-decision checkpoint" is `ckpt_040` for eight of the twelve runs and `ckpt_100` for the
other four — never assumed from the name, always read from the checkpoint's own sidecar
(`rlpd_ckpt.action_mode.json`, field `ckpt_step`). Every one of the 12 checkpoints used below was
selected this way and independently confirmed to carry `"ckpt_step": 100000` before being copied.

## 3. Evaluation command and hardware pin

One Slurm job per run (`$W/rl100_2026-09-11/rl100_eval.sbatch`, deployed **outside** the pinned
`gp_ladderN` tree per Lane 13's own corrected practice, §6.1 of the pilot log — code is read from
`GENESIS_PICKAPLACE_ROOT=$LAB/gp_ladderN`, every byte written under `$W/rl100_2026-09-11/`), three
cells per job, run sequentially in-job:

```
python baselines/eval_e2e.py --kind sac --checkpoint "$OUT_ROOT/<run>/ckpt_100/rlpd_ckpt.zip" \
  --ic-file baselines/eval_ics.json --ic-set <rnd|hold> --mode <mode|sample> --seed 0 \
  --out "$OUT_ROOT/<run>/<cell>" --records-out "$OUT_ROOT/<run>/records_<cell>" \
  --role record --require-cores 64 --device cpu --arm "<run>" --tag "<cell>"
```

Cells: `rnd30_mode` (`--ic-set rnd`, 30 episodes, `--mode mode`), `hold15_mode` (`--ic-set hold`,
15 episodes, `--mode mode`), and `rnd30_sample` (`--ic-set rnd`, 30 episodes, `--mode sample`) —
the third cell was cheap (same 30-start box, no extra checkpoint copy) so it was added per the
task's "add rnd30 SAMPLED if cheap." **900 episodes evaluated in total** (12 runs × 75).

run if a checkpoint disagreed with an explicit flag — there was no explicit flag to disagree.

## 6. The `home` / `farside` / `slide_event` finding, stated plainly

**Of the 900 episodes evaluated across all 12 runs at 100k decisions, exactly ONE reaches `home`:**
`e2e_rlpd_dDPfirst_s979` (staged + tip-guard control, machine-first, seed 979), `rnd30_sample`
cell, episode 19 (a random pose start, no demonstration uid), outcome `slide_success`, not tipped.
That single episode has `farside`, `slide_event`, `nested_v2`, `nested_honest`, and `home` ALL
true together — the full calibrated chain fires as designed, exactly once, and it happened under
the **control** ladder that never pays for it, not under `nested_ramp` or `nested_sparse`, which
do.

**No run under `nested_ramp` or `nested_sparse` — the two ladders built to pay for this behaviour
— has produced a single `home` at 100k decisions, in any of the 8 runs × 3 cells × ≤30 episodes
evaluated for them (630 episodes).** `nested_ramp` seed 971 and `nested_sparse` seed 976 machine
arms show `contact_push` and `slide_success` (the legacy per-frame predicates) firing on isolated
episodes, but never combine into `home`.

**Runs/cells that DO reach `farside` and/or `slide_event` without ever reaching `home`** (i.e. the
policy gets the gripper behind the can, and sometimes even registers goalward motion after
set-down, but the conjunction with a settled `nested_v2` never lands) — traced to individual
episodes via each cell's per-episode record:

Two seeds (`dH_s951`, `dDPfirst_s975`, `dH_s958`, `dDPfirst_s978`) never register a single
`farside` in any of their 75 evaluated episodes — the gripper never gets behind the can at all at
100k decisions for those four runs.

**Reading:** at 100k decisions, `farside` (arm behind the can after release) is a comparatively
common event across both `nested_ramp` and `nested_sparse` human and machine arms; `slide_event`
(≥1 cm goalward progress from that position, after a set-down) is rare (7 of 900 episodes, spread
over 4 seeds); and the conjunction with a settled `nested_v2` that defines `home` fires exactly
once in 900 episodes, on a seed from the arm that is not even paid to produce it. This is
consistent with — and at 100k decisions slightly ahead of — the pilot ladder's own trajectory
(PHASE_RESULTS §5.6: ~0 honest nests at 2M {r2dreamer} steps, 0.167 at 4.1M); it does not yet
distinguish `nested_ramp` from `nested_sparse`, or human from machine-first, on the slide behaviour
itself — the ramp's only visible effect so far is on `farside` touch rate and `picked`/`placed_v2`,
not on slide completion. **Do not read a human-vs-machine or ramp-vs-sparse contrast into this
table**: n=2 per arm at a single early checkpoint, exactly as amendment (aa)'s own registration
says ("NOT a source comparison (n=2 per arm)").

## 7. What this does and does not settle

- Settles the immediate question the task was launched to answer: **no, no Ladder N {RLPD} run has
  reliably learned to slide at 100k decisions** — the one `home` grant is a single episode, not a
  seed-level capability, and it belongs to the arm that isn't rewarded for it.
- Does **not** settle whether `nested_ramp` will out-slide `nested_sparse` at their full 250k
  budget, or whether {r2dreamer} (a different learner, 2M–4M online steps, still training) shows
  the same pattern — those are separate readouts.
- The training-record gap this lane was built to route around (`ep_farside` / `ep_slide_event` /
  `ep_home` absent from `episode_rollouts.jsonl`) is unresolved by this document; it is a code fix
  noted in HANDOFF §7b for the next batch, not something a checkpoint re-score can retrofit onto
  already-written records.
