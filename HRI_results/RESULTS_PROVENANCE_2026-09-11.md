# Results provenance — the ladder-unification work, 2026-09-10/11

Hand-maintained (not regenerated by `make_tables.py`). One question: **how would somebody rebuild
each artefact of the 2026-09-10/11 ladder-unification effort from raw inputs, and what check proves
the rebuild reproduced it?** Every command below is taken from the log or note that recorded it,
never from memory; the source is named at each step. Every claim about a file, a path or a job was
re-checked on 2026-09-11 against the branch and against the cluster, read-only, and is marked:

| mark | meaning |
|---|---|
| **[V]** | verified today — the path exists, the job is in `sacct`, the hash/count matches |
| **[V*]** | verified, and it **contradicts** a claim in the source document (the correction is given inline) |
| **[U]** | could not be verified from an artefact — the command is reconstructed and is marked as such |
| **[X]** | cannot be recreated at all — the inputs no longer exist, or the run was cancelled |

```bash
python3 - <<'EOF'
import numpy as np, glob, os, hashlib
W = "/cluster/tufts/shortlab/jstale02/wm_fix_2026-09-03/demos_state_full"
for src, dst in (("dHfull_all","dHfull_all_rz"), ("dHfull_all","dHfull_all_rs"),
                 ("dDPfull_first","dDPfull_first_rz"), ("dDPfull_first","dDPfull_first_rs")):
    diff, same, n = set(), 0, 0
    for p in sorted(glob.glob(f"{W}/{src}/*.npz")):
        a = np.load(p); b = np.load(f"{W}/{dst}/{os.path.basename(p)}"); n += 1
        for k in a.files:
            if k in b.files and not np.array_equal(a[k], b[k]): diff.add(k)
        same += int(hashlib.sha256(a["action"].tobytes()).hexdigest()
                    == hashlib.sha256(b["action"].tobytes()).hexdigest())

# expected: action sha identical 74/74 (or 72/72); arrays that differ == ['reward']
```

**Disclosed with the set, not discovered later** (amendment (z) §(z).3): `is_terminal` is left
exactly as recorded, so a relabelled tape may carry its recorded terminal at a different decision
from the re-execution's; `terminal_reward` and the other inherited manifest stamps describe the
SOURCE build, not this reward column; and re-execution fidelity is bimodal (`can_dev_max_m` p50
8.1 mm human / 10.8 mm machine, max 686 / 754 mm), with the divergence sitting **after** the grants
on every tape that pays the top rung except machine uid 302.

**Pairing rule, and why it is a rule.** The launcher takes the set from `DEMO`/argv and does **not**
check the suffix against `LADDER`. A mismatched pair trains a buffer on one objective and an
environment on another — the exact defect this whole amendment removes. `cluster/submit_lz_pilot.sh`
is the pairing of record: `_rz` with `staged`, `_rs` with `sparse`, nothing else.

### The stage-record method — **built for development, NOT the path of record**

A stage record is one `.npz` per tape with **one row per env frame** (4 per decision at
`action_repeat 4`), holding every input the stage predicates and the reward loop consume:
`can_pos/quat`, `goal_pos/quat`, `tool_xy`, `grip_cmd`, `picked`, `placed_v2`, the two
solver-contact booleans, the legacy stage flags, the tip flag and the reward the env paid, plus
scalars for the tape's identity, `shelf_top_z`, `max_steps`, the action sha256, one end-of-episode
settle (`nested_honest`) and the full ladder provenance. Each tape is re-executed **once** with
termination suppressed (`env.never_terminate`), so the record covers the whole action stream
whatever any ladder's terminal would have been.

The point: **a reward column does not steer the arm**, so one re-execution answers every candidate
ladder. Scoring a new ladder then costs seconds instead of a simulation pass.

intended path, from the cache's own README:

```bash
# build the records
python baselines/rl/relabel_reward.py --in  /home/j/data/genesis_pickaplace/demos_state_full/<set> \
    --records-out /home/j/data/genesis_pickaplace/stage_records/<set> --procs 8
# score any ladder offline against them
python baselines/rl/relabel_reward.py --in <source set> --out <set>_rnr \
    --from-records /home/j/data/genesis_pickaplace/stage_records/<set> --ladder nested_ramp [--far-release]
# the offline path and a direct re-execution are asserted equal (reward column AND terminal decision)
python baselines/rl/relabel_reward.py … --verify-against <direct re-execution>
```

**[U] These flags are NOT on `ladder-unify-2026-09-11`.** `--records-out`, `--from-records`,
`--verify-against`, `--far-release` and the `nested_ramp` ladder exist only in Lane 7's worktree
commits `cf66293` and `61dbea6` (both are real objects in this repo **[V]**, on branch
`worktree-agent-a60a2275c95f8dfd8`, unmerged). The records in the cache were built from `cf66293`.
Until that merges, the recipe above cannot be run from the branch of record.

**The caveat that decides citability**, quoted from the cache README: the records were made on
**pop-os, AMD Ryzen 9 5950X, 32 cores, AVX2** — not the cluster's 64-core class. The same human set
pays Σ **179** here where the cluster pays Σ **171** under `staged`. **Records of record must be made
on the 64-core class**; regenerating there costs one pass (~9 min wall on 8 cores per set) and every
